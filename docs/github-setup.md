# Connect Bivy to your GitHub

Bivy touches GitHub in two unrelated ways, set up separately:

| | What it's for | Who sets it up | Doc |
| --- | --- | --- | --- |
| **GitHub OAuth App** | "Sign in with GitHub" for the web app, mobile PWA, and CLI | An operator, once, on the control plane | [github-oauth-setup.md](github-oauth-setup.md) |
| **GitHub App** | Turning labeled issues into agent runs that open pull requests (the work queue) | You, per GitHub account/org you want Bivy working in | this page |

If you just want to log in, you're in the wrong doc — go to
[github-oauth-setup.md](github-oauth-setup.md) (or just click "Sign in with
GitHub"; that part is already configured for Bivy Cloud). This page is about
the second one: letting Bivy see and act on issues in your repositories. For
how the work queue actually behaves once connected — routing labels, what gets
stored, failure handling — see [github-work-queue.md](github-work-queue.md).
This page is only the "how do I connect it" walkthrough.

## Why "connect GitHub" means creating an app, not granting a token

Bivy uses a **GitHub App**, not a personal access token or a single shared
OAuth app. One app covers every repository you install it on with one
webhook — no per-repo webhook, no repo-admin token living anywhere. The app's
private key is generated by GitHub, delivered to your Bivy **node**, and kept
in the node's secret vault. The control plane never sees it.

## The multi-app model: one private app per account/org

This is the part that trips people up. GitHub Apps are usually created
**private** by Bivy's flow, and a private app can only be installed on the
single GitHub account or organization that owns it — that's a GitHub
constraint, not a Bivy choice. Practically, that means:

- A GitHub App you create under **your personal account** can only be
  installed on your personal repositories.
- A GitHub App you create under **an organization** can only be installed on
  that organization's repositories.
- **One app cannot cover both.** If you want Bivy working in your personal
  repos *and* in `acme-corp`, you need **two apps**: one owned by you, one
  owned by `acme-corp`. Want a third org too? A third app.

(The alternative — making an app public so anyone can install it anywhere —
is deliberately not the default flow: a public app can be installed by
anyone, and every installation delivers to *your* webhook. Don't do this
unless you specifically want that.)

A single node can hold several of these apps at once. Each keeps its own
private key in the node's vault, its own webhook, and its own `@`-mention
handle — mentioning one app's bot never triggers another app connected to the
same node. When Bivy needs a token for a specific repository, it picks
whichever connected app is actually installed there, preferring the app owned
by that repo's own account/org.

## Connect your personal account

Pick whichever is easiest for how you're running Bivy:

**From the web app** (works against a hosted or self-hosted control plane, or
a local node):

1. **Settings → GitHub App → Create GitHub App.**
2. Approve the one-click manifest flow on GitHub. Bivy creates the app,
   GitHub hands the credentials back, and your node stores the private key.
3. On GitHub, install the app on the repositories you want Bivy to see.

**From the CLI**, on the node itself:

```bash
bivy github:app-create
```

This drives the same manifest flow, opening a browser for you. On a headless
server it instead prints alternatives: run it from the web app, tunnel a
browser to the node over SSH, or create the app manually on GitHub and
connect it with:

```bash
bivy github:app-connect --app-id <id> --key ~/path/to/private-key.pem
```

## Connect an organization

Same flow, but tell it which org so GitHub creates the app there instead of
under your personal account:

- Web app: **Settings → GitHub App → Add an app**, and fill in the
  organization field.
- CLI:

  ```bash
  bivy github:app-create --org acme-corp
  ```

Repeat this once per organization you want Bivy working in. Each creates a
distinct app, owned by that org, installable only on that org's repositories.

## Using it from more than one node

By default a connected app's private key lives only on the node that ran
`github:app-connect`/`github:app-create` — a second node, or a fresh
machine, has no key and can't serve that app's work until it's connected there
too. To let an app connected on one node also serve your OTHER nodes without
re-uploading the `.pem` anywhere, opt each of them in:

```bash
bivy github:app-sync on
```

This is off by default and per node, on purpose: a GitHub App key is a
repo-write credential, so which nodes hold it should be a deliberate choice,
not automatic. Once two or more nodes have it on, a `github:app-connect` done
on any one of them reaches the others automatically — E2E-encrypted the same
way model/provider auth already syncs between nodes; the control plane relays
ciphertext it cannot read. See
[credential-sync.md](credential-sync.md#4-github-app-private-keys) for the
mechanics, and `bivy github:app-sync` (no argument) to check whether a node
has it on and which apps it currently holds.

## Put it to work

Once an app is installed on a repository:

1. Add the `bivy` label to an issue (or `@`-mention the bot in a comment) to
   route it to your default/shared queue.
2. Add a node-specific label instead, e.g. `bivy/macbook`, to target one
   machine.
3. Bivy picks up the issue on a matching connected node, works it in an
   isolated worktree, and opens a pull request back to the same repository.

Full mechanics — the pickup/in-progress/PR label lifecycle, what happens if
no node is online, what gets stored where — are in
[github-work-queue.md](github-work-queue.md#routing-labels). If you'd rather
route all untagged/`@`-mention-only work to one particular machine instead of
leaving the bare `bivy` label as free-for-all, set **Settings → GitHub App →
Default node**.

## Disconnecting

Web app: **Settings → GitHub App →** pick the app **→ Disconnect**. The node
stops handling that app and wipes its copy of the private key; the control
plane drops the webhook registration so it stops routing. This does **not**
delete the app on GitHub — do that from GitHub's own app settings
(`https://github.com/settings/apps`, or the org equivalent) if you want it
gone entirely, not just disconnected from this node.

## Troubleshooting

- **Nothing happens when I label an issue.** Confirm the app is actually
  installed on that repository (GitHub → the app's settings →
  **Configure**), and that a node serving that label (`bivy`, or the specific
  `bivy/<node>` you used) is online — check `bivy status`/`bivy doctor` on
  that node.
- **Wrong app answered a mention in an org repo.** Each app has its own
  mention handle; if two accounts/orgs both have Bivy apps installed on
  overlapping repos, double check which app's manifest name you're
  `@`-mentioning.
- **`bivy github:app-create` on a headless server does nothing visible.** It
  needs a browser that can reach the node's local port. Use the web app flow,
  an SSH tunnel, or create the app manually + `github:app-connect`.
- More failure modes (offline nodes, races between two eligible nodes, no
  changes produced) are covered in
  [github-work-queue.md § Failure behavior](github-work-queue.md#failure-behavior).
