## [Unreleased]

### Added
- **Tag-triggered npm release workflow with provenance** (issue #6). `npm run publish:npm` existed but nothing called it, so releases were a manual, unattested `npm publish`. A new `.github/workflows/release.yml` runs on every `v*` tag push: it reuses the full CI gate (`.github/workflows/ci.yml`, now also a `workflow_call` target) before publishing, verifies the tag matches `package.json`'s version, publishes via npm [Trusted Publishing](https://docs.npmjs.com/trusted-publishers/) (`permissions: { id-token: write }`, no `NPM_TOKEN` secret — the OIDC identity authenticates the publish and provenance is attached automatically), and creates the GitHub release from the matching `## [x.y.z]` section of `CHANGELOG.md` (new `scripts/extract-changelog.mjs`). Documented in `docs/releasing.md`, including the one-time manual bootstrap publish trusted publishing requires before it can be configured.
- **Multiple GitHub Apps per account.** A *private* GitHub App can only be installed on the account that owns it, so a single app could never cover both a user's personal repositories and their organizations — and making it public would let anyone install it and enqueue work against the owner's account. A node now serves several apps: one per GitHub account/org. Each keeps its own private key in the node's vault (`github.app.<appId>`, tracked in a new `<dataDir>/github-apps.json` registry), its own control-plane webhook, and its own `@`-mention handle, so mentioning one app never triggers another. Work items now carry the `appId` of the hook that received the delivery, so the node knows which key to mint with instead of guessing; repo→installation lookups try the app owned by that same account first, keeping the common case to a single API call. Settings → GitHub App lists every connected app with its owner, install count, and serving node, and disconnect is per-app. `bivy github:app-create --org <org>` creates an app under an organization. The single-app environment configuration (`BIVY_GITHUB_APP_ID`) still works and is surfaced as one registry entry, so container and ephemeral-runner setups are unaffected. (`src/github-apps.ts`, `src/server.ts`, `src/github-app-connect.ts`, `services/control-plane/src/{store,postgres-store,index}.ts`, `packages/core/src/account.ts`, `packages/web/src/components/Settings.tsx`, `packages/web/src/components/GithubQueue.tsx`.)

### Fixed
- Direct-mode `github.app.disconnect` sent an empty body, so disconnecting a single app would have wiped every GitHub App key on the node. It now forwards the `appId`. (`packages/core/src/transport-direct.ts`.)

## [0.1.0] - 2026-07-21

First public release.

Bivy runs coding agent CLIs on machines you own and makes those sessions
reachable from a phone, browser, or another terminal. This release marks the
point at which the node daemon, CLI, relay, control plane, and web client are
published as source-available software.

### Highlights

- **Ten agents through one interface** — Pi, Claude Code, Codex, OpenCode,
  Gemini CLI, Qwen Code, Goose, Aider, Cline and Crush, each driven through its
  native CLI in a real PTY. Any other command runs via `bivy run -- ./your-agent`.
- **Durable sessions** — an append-only event log and a dedicated git worktree
  per session. Sessions survive detach, daemon restart, and reconnection from a
  different device.
- **Remote access without inbound ports** — the node dials out to a relay that
  forwards end-to-end encrypted frames. Device pairing uses X25519 + HKDF; the
  relay and control plane see ciphertext only.
- **Approvals** — risky shell commands and file edits pause for in-chat
  approval; safe read-only commands run automatically. Modes: `never`, `risky`,
  `always`, `autonomous`.
- **Session forking** — continue a session on a different agent, model, or
  machine, carrying the transcript and uncommitted work.
- **GitHub work queue** — label an issue `bivy` or mention the GitHub App, and a
  node you own claims it, works in an isolated worktree, and opens the PR.
- **Terminal takeover** — `bivy shim install <agent>` makes the native TUI start
  inside a Bivy PTY, so an ordinary terminal session becomes remotely drivable.
- **Credentials stay local** — encrypted vault with `secret://`, `env://`, and
  `op://` (1Password) references resolved before the daemon starts.
- **Any model endpoint** — thirteen providers by API key or OAuth, plus
  self-hosted OpenAI-compatible, Azure, Ollama, LM Studio, vLLM and SGLang.
- **Bring-your-own-cloud runners** — short-lived machines on Fly.io, Hetzner, or
  AWS EC2 using a provider token that stays on your device.
- **Signed releases** — the installer verifies a SHA-256 digest and an Ed25519
  signature over the release manifest, and fails closed.

### Known limitations

- Bivy does not ship an OS-level sandbox jail. Sandbox tiers are enforced
  natively by agents that support them; others are governed at the filesystem,
  MCP, and network layer.
- Queued GitHub issue titles and bodies are stored in plaintext by the control
  plane until a node claims them.
- Credential sync between your own nodes covers Bivy-managed provider keys;
  agent-native logins remain per-machine.
- Aider and Crush cannot resume a session (upstream gaps).
- Self-hosting is unsupported: no SLA, community best-effort.

### Added
- **On-demand GitHub PR status refresh — in-session command + global scan** (issue #530). PR state was only reconciled opportunistically, via `refreshPullRequests` running after each turn (`maybeDetectPullRequest`) — a session that finished, was saved, or wasn't attached kept whatever `open`/`merged`/`closed` badge it last saw until something made it take another turn, even after the PR merged on GitHub. A new `/github-status` command (mirrors `/pr` — server command table, `SLASH_COMMANDS`, and an "Update GitHub status" button next to "Create pull request" in both the sidebar row menu and the session header menu) force-runs `refreshPullRequests` for the current session regardless of live/attached state, resuming it first if the node dropped it from memory (`session.pr.refresh` relay command, `POST /api/session/pr/refresh`). A new "Refresh GitHub status" button (GitHub Queue settings page) scans every session the node has ever tracked that carries PR state (`metadata.listSessions()`, not just the currently-open ones) and reconciles each against GitHub with bounded concurrency (`refreshAllPullRequestStatuses`, capped by the existing GitHub-queue concurrency setting) — live sessions go through the full transcript-aware `refreshPullRequests`, everything else through a new lighter `refreshPullRequestsForMeta` that reconciles straight against the persisted metadata row without spinning up a runtime per session. Only sessions whose PR state actually changed persist + broadcast. (`src/server.ts`, `packages/core/src/slash.ts`, `packages/core/src/protocol.ts`, `packages/core/src/transport-direct.ts`, `packages/core/src/store.ts`, `packages/web/src/store/controller.ts`, `packages/web/src/App.tsx`, `packages/web/src/components/SessionList.tsx`, `packages/web/src/components/SessionMenu.tsx`, `packages/web/src/components/GithubQueue.tsx`.)
- **Node stats are reachable from node settings** (issue #463). The **Settings → Nodes** panel now has a "View node stats →" button that opens the existing live memory/CPU/storage `StatsPanel` (Sheet), scoped to whichever node the panel is currently editing/connected to — no more needing an active session's header menu just to check a node's resource usage. Purely a UI wire-up; the stats plumbing (`node.stats` request/event, `collectNodeStats`) is unchanged. Bumped `.sheet`'s z-index (70 → 76) so it layers above `.settings-modal` (75) instead of behind it when opened from within Settings. (`packages/web/src/components/Settings.tsx`, `packages/web/src/styles.css`.)

### Changed
- **GitHub issue pickup now visibly signals itself on the issue, for every pickup path** (issue #458). Previously only the legacy direct-repo poller ever touched the issue's labels on pickup, and no path ever commented — a human watching an issue (especially through the hosted GitHub App queue, the recommended setup) had no on-issue sign that Bivy had started. `announcePickup` (`src/github-tasks.ts`) now runs at the start of every fresh pickup (`runIssueTaskInner` in `src/server.ts`, covering the direct poller, the hosted GitHub-App work queue, `@`-mentions, and the manual "Run…" queue action alike): it adds `bivy:in-progress`, removes the routing label that triggered it (e.g. `bivy` → `bivy:in-progress`), and comments "Bivy has picked this up and started working on it on node `<name>`". `reportIssueOutcome` now also removes `bivy:in-progress` once the agent's pull request is open, so the label doesn't linger once the linked PR is the live signal — label state stays consistent through the pickup → in-progress → PR lifecycle instead of accumulating. Branch/PR linkage back to the issue (deterministic `bivy/issue-<n>` branch, PR comment, `GithubPill`/`GithubQueue` UI) already existed and is unchanged. (`src/github-tasks.ts` — new `removeLabel`, `pickupMessage`, `announcePickup`; `src/server.ts`; `test/github-tasks.test.ts`; `docs/github-work-queue.md`; `docs/github-agent-workflow.md`.)

### Fixed
- **Renaming a node no longer leaves a phantom duplicate in the GitHub App "Default node" selector** (issue #464). The account's default-node routing (`inbound_hooks.default_node` / `InboundHook.defaultNode`) is stored as a plain *name*, not a stable node id — human-readable for the `bivy/<name>` routing label, but a rename orphaned it: the control plane kept the old name on the hook while the node's own record moved to the new name, so `GET /account/github-app` and the live `GET /nodes` list disagreed. Settings → GitHub App's "Default node" `<select>` (and the GitHub Queue's per-item "Run…" node picker) both render a defensive fallback `<option>` for a saved value that matches no listed node, which turned that mismatch into what looked like the same node appearing twice — once under its old name, once under its new one. `setNodeName` (`services/control-plane/src/store.ts`, `postgres-store.ts`) now rewrites any of the account's inbound hooks whose `defaultNode` equals the node's previous name to the new one in the same rename call (transactional in the Postgres store), so the reference always tracks the node it actually points at. (`services/control-plane/src/store.ts`, `services/control-plane/src/postgres-store.ts`, `services/control-plane/test/store.test.ts`.)
- **`bivy uninstall --keep-sessions` sessions now actually survive a reinstall** (issue #461). The flag used to move only the raw pi transcripts (`.bivy/pi/sessions`) aside to a one-off `~/bivy-sessions-<timestamp>` folder that nothing ever restored — the durable session index (`.bivy/metadata.json`, which `listAllSessions` relies on to union in closed/PWA-started sessions and backfill names, branch, and PR info) was deleted regardless of the flag, so both the CLI and the React app showed nothing after a fresh install. `bivy uninstall` now deletes everything under the app's state dir *except* those two paths when `--keep-sessions` is set (new `removeExcept`, replacing the old move-aside), leaving them exactly where a rerun of a dev checkout, or `install.sh`'s own `.bivy` carry-forward on a packaged reinstall, already looks for them — so kept sessions are rediscovered automatically with no manual restore step. (`bin/bivy.mjs`.)
- **`bivy update`/`bivy restart` no longer kill a live agent mid-turn** (issue #474). Restarting the service SIGTERMs every open session's runtime process; done while a session was mid-reply or mid-tool-call, that corrupted the turn outright instead of just delaying it. `/api/status` now reports `sessions.busy` — the count of sessions currently streaming a reply or running a tool (`sessionBusy`, already used to protect a busy session from deletion). Before restarting, the CLI polls that count and waits for it to hit zero, logging progress, with a bounded 30-minute grace period (`BIVY_UPDATE_WAIT_TIMEOUT_MS` to override, `0` to disable) so a wedged session can't block an update forever; `--force`/`--no-wait` skips the wait outright. Applies to every path that restarts the service — `npm i -g` updates, git-checkout updates, and the packaged install.sh flow (which restarts via `bivy restart` using the freshly-updated binary) — plus the explicit `bivy restart` command. (`src/server.ts`, `bin/bivy.mjs`.)

### Changed
- **Issue sessions: the agent creates its own PR, guided by a user-editable prompt** (issue #459). The node no longer commits, merges, pushes, or opens/updates a pull request on the agent's behalf for GitHub-issue pickups — that hard-coded automation is gone. Instead, the first message sent to the agent (`buildTaskPrompt`/`DEFAULT_ISSUE_INSTRUCTIONS` in `src/github-tasks.ts`) asks it to understand the issue and the codebase, do thorough work, run the project's tests/linter/type-checker and fix what they find, then commit, push, and open the pull request itself — referencing/closing the issue. Those instructions ship with a strong default but are user-editable per node: **Settings → Nodes → GitHub issue prompt** (new `githubIssuePrompt` node setting, `packages/core/src/store.ts` `NodeSettings`, `packages/web/src/components/Settings.tsx`), with a one-click reset to the shipped default. The node still helps without writing anything: `repoSessionParts` now recognizes issue-sourced sessions (`issue:owner/repo#N`) as well as regular repo sessions, so the same after-turn hooks apply to both — publish the branch if the agent didn't push it (`maybePushWorktreeBranch`), adopt a PR the agent opened itself (`maybeDetectPullRequest`), and offer the manual `/pr` chat command as a fallback. A lightweight `reportIssueOutcome` (replacing `finalizeIssueWork`) comments on the issue with the outcome — the PR link, "no changes", or "pushed but no PR yet" — without ever writing the PR's title or body itself. Follow-up `@`-mentions still get the branch synced with the base (and merge conflicts handed to the agent) before their turn runs, but the agent now owns committing/pushing/opening-or-updating the PR there too. (`src/github-tasks.ts`, `src/server.ts`, `test/github-tasks.test.ts`, `docs/github-work-queue.md`, `docs/github-agent-workflow.md`.)

### Added
- **A standalone (session-less) terminal, reachable from the sidebar** (issue #460). A new terminal button sits to the left of "+ New"; clicking it opens the picked node's default workspace folder in a plain shell that isn't tied to any chat session — no more starting a throwaway session just to run a command. Picking a node is skipped automatically when there's only one to choose from (direct/local mode, or a single-node relay account); otherwise a node picker (`NodePicker` in `Pickers.tsx`) opens, defaulting to the current node. The node's `terminal.open` handler now honors a `standalone` flag that roots the shell at the node's default workspace instead of falling back to the active chat session's cwd, so it stays independent even while a session is open on that node. The terminal header shows the resolved workspace folder for context. - **Four more agent capabilities in the general layer** — token usage, reasoning-effort selection, a reasoning/thinking stream, and model selection over the protocol — each taught once in the shared layer, expressed per-agent as data:
  - **Usage reporting for CLI agents.** The structured parsers now extract token counts from the agent's own output via a key-spelling-agnostic scan (`extractTokenUsage` — handles OpenAI/Anthropic/Gemini/Goose spellings), `ProcessSession.getUsage()` surfaces the latest turn's snapshot, and `capabilities.usageReporting` is advertised only for the agents whose parser emits tokens (Gemini/Qwen `gemini-json`, Goose `goose-stream-json`). Powers the cost/context meter on `agent_end`.
  - **Reasoning / thinking stream.** Reasoning the agents already emit but we discarded (Codex `reasoning` items; protocol `message.reasoning`) now surfaces as the same collapsible `{type:"thinking"}` intermediate block the daemon renders for Pi/Claude — kept out of the answer text and out of persisted history.

  - **Model selection over the bivy-agent-protocol.** `ProtocolSession.setModel` no longer throws "not implemented": a shim advertises a model registry in its `hello` (`runtime.models`), the host derives `modelSelection` from it, `getModels()` returns the list, and `setModel()` forwards a `model.set` command the shim acknowledges. The protocol also carries `usage` and `message.reasoning`. They are driven through Bivy's existing general paths (the native runtimes, the Codex app-server shim, and the data-driven `ProcessRuntime` + `CliParser` path), not bespoke per-agent adapters — adding an agent stays O(1) as a row of data in `CLI_AGENT_SPECS`. Details:
  - New agents `qwen`, `cline`, `crush` are pure data. **Qwen Code** (a Gemini-CLI fork) reuses the `gemini-json` parser and `--approval-mode` containment.
  - A **generic, data-driven resume primitive** (`spec.resume.template` + a `BIVY_<ID>_RESUME_TEMPLATE` override with `{id}`/`{tier}` placeholders) lets any CLI with a known resume form become resumable with zero per-agent code; capabilities stay honest (resume is reported only when a template exists).

### Removed
- **The Bivy-owned OS exec jail (Level B) is gone for v1.0.** The bubblewrap/`sandbox-exec` jail wrapped every agent and terminal in an OS sandbox scoped to the worktree, but it was opt-in, host-dependent, and crashed some nodes outright — inside nested containers `bwrap --unshare-net` aborted before the agent ran with `loopback: Failed RTM_NEWADDR: Operation not permitted`, blocking every file and shell op. It's removed as out-of-scope for v1.0 (may return later). Agents keep enforcing their own native sandbox (Level A — Codex `--sandbox`, Gemini `--approval-mode`, Claude `permissionMode`, still selected by `BIVY_SANDBOX`); agents without one stay governed by the filesystem/MCP/network channels. Dropped `BIVY_EXEC_JAIL`, `BIVY_EXEC_JAIL_READS`, `bivy doctor --sandbox`, and the `execJail` block of `/api/node/info.sandbox`. (Removed `src/harness/exec-jail.ts`, `src/doctor.ts`, `docs/harness-exec-sandbox.md`, `test/harness-exec-jail.test.ts`; updated `src/runtime/process.ts`, `src/terminal.ts`, `src/server.ts`, `src/harness/sandbox.ts`, `bin/bivy.mjs`.)

### Changed
- **The React client (`@bivy/web`) is now the only web UI, served at the root.** The legacy hand-written vanilla client (`public/remote.html` + `public/app/*`, and its `services/control-plane/public/` mirror) has been removed, along with the `/next` migration path. Both surfaces now serve the built React app at `/`: the control plane (`app.bivy.sh`) and the node daemon (`http://localhost:4317`, including the local `?local=1` direct-mode UI). Sign-in link/QR URLs dropped `/remote.html` (now `…/#<payload>`), the PWA manifest scope/`start_url` moved to `/`, and the node daemon now sends the app shell the same locked-down CSP the control plane applies. (`packages/web/vite.config.ts`, `src/server.ts`, `services/control-plane/src/index.ts`, `deploy/Dockerfile.control-plane`, `bin/bivy.mjs`.)

### Changed
- **The GitHub issue → PR flow is titled, self-describing, conflict-aware, and answers follow-ups.** Four improvements to `runIssueTask` (`src/server.ts`) and the git helpers (`src/github-tasks.ts`, `src/worktree.ts`):
  - **Issue sessions are titled up front.** A pickup session used to show as "Untitled session" until (if ever) named; it now takes the issue's title + number (`Ui review react app (#370)`) the moment it's created, deterministically, so it reads well in the sidebar regardless of runtime. (`setSessionName`/`issueSessionTitle`.)
  - **Agent-written PR title + description.** The PR no longer opens with the raw issue title and a one-line boilerplate body. The node summarizes the branch's own diff with its Anthropic credential (`generatePrContentFromNode`, same credential seam as session naming — works for every runtime) into a concise imperative title and a short Markdown description; `Resolves #N` and the footer are always appended, and it falls back to the deterministic issue-derived text if naming is unavailable. It's regenerated on every run, so a follow-up refreshes the summary of a now-stale PR (`updatePullRequest`). (`branchDiff`, `parsePrContent`, `buildPrBody`.)
  - **Automatic merge-conflict resolution.** Before opening/updating the PR the branch is merged up to the base (`mergeBaseIntoBranch`); on a conflict the agent is asked to resolve it in place (`buildConflictPrompt`) and the merge is completed (`completeMerge`, which refuses to commit a tree that still has conflict markers). If it can't be resolved the merge is aborted and the PR is opened anyway with a warning comment, instead of the branch silently landing as "Unable to merge".
  - **Follow-up @-mentions continue the session.** A second `@`-mention on an issue used to try to recreate the existing `bivy/issue-N` branch, fail, and get silently marked "done" with nothing happening. A live issue session is now reused — the comment runs as another turn in the same worktree and the existing open PR is updated (`runIssueFollowUp`/`finalizeIssueWork`); if the session is gone, `createWorktree` now adopts the existing local/remote branch instead of colliding. All work for one issue is serialized (`withIssueLock`) so a follow-up and the first run (or two quick follow-ups) can't drive the same worktree/branch/session concurrently. (`test/github-tasks.test.ts`, `test/worktree.test.ts`.)

### Fixed
- **A failed GitHub sign-in is now diagnosable instead of a dead end.** The OAuth callback used to collapse three unrelated failures — a token exchange that never returned an access token (rotated `GITHUB_OAUTH_CLIENT_SECRET` or a `PUBLIC_CONTROL_PLANE_URL`/`redirect_uri` mismatch), a granted token missing the `user:email` scope, and a GitHub account with no verified email — into one message ("Could not read a verified email from GitHub") and logged nothing, so a fresh server install that failed here gave the operator no clue why. `githubPrimaryEmail` now returns a typed failure reason, logs the specific cause of every branch server-side (including GitHub's `error`/`error_description`, which it returns with an HTTP 200), and the browser shows failure-specific copy that points at the real fix. Documented the two new cases in `docs/github-oauth-setup.md`. (`services/control-plane/src/index.ts`, `docs/github-oauth-setup.md`.)
- **`bivy shim install` now makes the shim reliably win on PATH — no manual rc editing.** Installing a shim into `~/.local/bin` only intercepts an agent if that dir beats the real binary on your *interactive* PATH, which it usually didn't: version managers (mise/asdf/nvm/pyenv) prepend their bin dirs from shell-init hooks that run *after* any static `export PATH="$HOME/.local/bin:$PATH"`, so the real binary kept winning and the shim never fired — while the installer wrongly reported "Active" because the `bivy` process's own PATH is front-loaded with `~/.local/bin`. Now `install` writes a clearly-marked, idempotent block to the **end** of your shell rc (`~/.zshrc`/`~/.bashrc`), after the version-manager init, that force-moves every shim dir to the front of PATH (valid in bash and zsh; de-dupes and re-anchors on each run, and is auto-removed when the last shim is uninstalled). `install`/`status` now verify through a fresh interactive login shell, so "active/shadowed" reflects your real PATH rather than the doctored process PATH; non-bash/zsh shells fall back to printed manual instructions. (New `bin/shim-path.mjs`; `bin/bivy.mjs`, `docs/agent-shim.md`, `test/shim-path.test.ts`.)
- **GitHub sign-in flow on mobile now lands the user back in the app.** Three fixes to the hosted sign-in path (React client):
  - The "You're signed in" page no longer strands the user. In the installed-PWA device flow the app opens the OAuth tab itself and polls for completion, so once sign-in lands that tab has done its job — it now closes itself and hands focus straight back to the app instead of showing a dead-end page. (Email/QR device-flow tabs, which the app didn't open, keep the message.) The self-close snippet is whitelisted for just that response via a CSP hash, so the global `script-src 'self'` stays intact everywhere else. (`services/control-plane/src/index.ts`.)
  - Signing in no longer drops the user on a full-screen "Choose a node" wall. Once signed in the app always renders the normal sidebar/new-session shell; a node is picked in-place from the header switcher (with an inline hint until one is chosen), so a refresh lands on the app rather than the picker. This also removes the standalone `NodePicker` screen whose full-screen→app remount could flash a blank page on node select. (`packages/web/src/App.tsx`, removed `packages/web/src/components/NodePicker.tsx`.)
- **GitHub sign-in no longer loops for a client served under a sub-path.** The OAuth callback hard-coded a redirect to root; it now honors a validated same-origin `return` path threaded through the OAuth `state`, so a sign-in started from a sub-path lands back there. (`services/control-plane/src/index.ts`, `services/control-plane/src/redirect.ts`, `packages/web/src/components/SetupNotice.tsx`.)
- **Opening a session from the sidebar no longer corrupts its row (React app).** Clicking a stored session resumes it on the node, which re-broadcasts `session.created` — but that event carries no name and no fresh timestamp, and the resumed runtime session started nameless. Three consequences, all fixed:
  - The header title never updated on open (it stayed on the previous session's title). The node now restores the session's canonical name onto the resumed runtime so `session.history` carries it, and the client also paints the known row's name into the header immediately on open. (`src/server.ts`, `packages/core/src/store.ts`).
  - The sidebar row flipped to "Untitled session". The resumed session's empty name was persisted over the stored one; the node now restores the name before persisting, and the client's `session.created` reducer no longer defaults an *existing* row's name to "Untitled". (`src/server.ts`, `packages/core/src/store.ts`).
  - Merely opening a session bumped it to "active just now". Opening now preserves the stored last-active time instead of stamping `Date.now()` (server + client), so the sidebar only reorders on real user/agent activity. (`src/server.ts`, `packages/core/src/store.ts`). Regression tests in `packages/core/test/store.test.ts`.
- **The error toast now shows the full message (React app).** It truncated errors to ~117 characters on a single ellipsized line (the rest was only in a hover tooltip — invisible on mobile), so a 401 read as `unexpected status 401 Unauthorized: Miss…`. It now renders the whole message, wrapped and capped to the viewport height (scrolls if taller), and lingers longer for longer messages. (`packages/web/src/components/ErrorToast.tsx`, `packages/web/src/styles.css`).
- **New sessions no longer die with an opaque `unexpected status 401 Unauthorized: Missing bearer …`.** Selecting an agent that had no usable model credential on the node let it launch and fail its very first API call with the raw upstream 401 (the error surfaced verbatim as a composer toast). Two gaps closed:
  - Bivy now runs a **credential preflight** before starting a turn and, when the selected agent has no credential it can use, surfaces a clear, actionable message (add a key under Models & providers, or sign in on the node) instead of the cryptic 401. Covers the Claude Code SDK (`ANTHROPIC_API_KEY` / `CLAUDE_CODE_OAUTH_TOKEN` / `claude` `/login`; Keychain logins on macOS are never false-blocked) and the Codex CLI (`OPENAI_API_KEY` / `codex login`; a ChatGPT/Codex subscription signed into Bivy can't be handed to the Codex CLI). (`src/runtime/anthropic-preflight.ts`, `src/runtime/codex-preflight.ts`, `src/runtime/claude-code.ts`, `src/runtime/process.ts`, `src/runtime/index.ts`).
  - The Claude Code SDK runtime **no longer swallows thrown errors**: a failed query (e.g. an auth 401) emitted `agent_end` with an `error` field the client never reads, so the turn stopped silently. It now emits a `session.error` (the toast path) with sign-in guidance appended to auth failures. Tests: `test/anthropic-preflight.test.ts`, `test/codex-preflight.test.ts`, and a `ProcessRuntime` preflight case in `test/runtime-cli-parsers.test.ts`.
- Switching agents from the composer pill now sticks. Selecting a different agent (e.g. Codex → Pi) with no live session fired a `models.list` immediately after `runtime.select`; the two raced on the node, so the model list was built against the *old* runtime and — because model queries spun up the node-global `active` session — the agent pill silently reverted on the next open and the model picker showed nothing. The client now lets the node's `runtime.updated` broadcast (sent only once the switch lands) refresh the models, and model/thinking reads reuse a non-active scratch session so they never hijack the active agent (`src/server.ts`, `public/app/remote-app.js`, `services/control-plane/public/app/remote-app.js`).
- Model picker now shows providers signed into *after* a session was opened. The Pi runtime's model registry cached an in-memory snapshot of `auth.json` at session start, so an OpenAI/ChatGPT (or any other) OAuth sign-in done while a Claude session was open never surfaced — the picker kept listing only Claude. `getModels()`/`setModel()` now reload the shared credential vault so freshly-added providers appear immediately (`src/runtime/pi.ts`, regression test `test/pi-models-auth-refresh.test.ts`).

### Added
- **`bivy shim install <agent>` — start an agent from your terminal, reach it from the phone.** A shim shadows an agent's binary on `PATH` so that starting it interactively (e.g. typing `claude`) transparently launches it **inside a Bivy-owned PTY** (via `bivy run <agent>`) instead of a bare process. You still get the agent's **native TUI** locally; because the daemon owns the PTY, the *same live session* is visible and drivable from the remote web/PWA ("continue on CLI"). The session id is **pinned at launch** for agents whose CLI supports it (`claude --session-id <uuid>`, unless you already passed `--resume`/`-c`/`--session-id`), so the on-disk session is a deterministic resume target — the anchor for a later "continue as chat" takeover. Headless invocations (non-TTY stdin — pipes, scripts, CI — or a one-shot flag like `claude -p`, `codex exec`, `goose run`) `exec` the real binary unchanged; that passthrough is also the recursion guard for the agent subprocess a resumed session itself spawns. The mechanism is agent-agnostic (PATH shadowing, real-binary resolution, the `bivy run` handoff are identical for all agents; per-agent knowledge is just a small "headless flags" list, with a safe default and a `--headless` override, plus an optional session-id flag). Aliased as `bivy listen`. Manage with `bivy shim status` / `bivy shim uninstall <agent>`; bypass a shim for one run with `BIVY_SHIM_DISABLE=1 <agent>`. Registry in `.bivy/shims.json`. (`bin/bivy.mjs`, `docs/agent-shim.md`.)
  - **"Continue as chat" takeover** — `bivy takeover <termId|session-id>` (and `POST /api/terminals/takeover`) stops the native TUI running in a pinned run-terminal and reopens its pinned session as a **governed, structured chat** on the owning runtime. The pinned session id is the resume target; closing the terminal SIGTERMs the PTY (the kill target), so there is never a second live writer. Supported today for agents with a resumable, tool-intercepting runtime (Claude, Pi); the response returns the `--resume` command to hop back to a terminal. Each run-terminal now carries its pinned `sessionId` and PTY `pid` (`GET /api/terminals`, `terminal.created`) so a client can offer the action. (`src/server.ts`, `src/terminal.ts`, `src/attach.ts`, `bin/bivy.mjs`.)
  - **Codex structured-resume takeover** — Codex sessions can now be reopened as a live *structured chat*, not only read-only. `ProcessRuntime` gained an opt-in resume path (`resumable` + `resumeArgs(id)` + `loadHistory(id)`); Codex enables it (`resume: true`), so "Continue as chat" discovers the session by cwd (`discoverCodexSessionForCwd`), stops the TUI, and reopens it via `codex exec resume <id> --json` with history preloaded from the rollout. Governance is effect-level (the exec jail), not per-tool approval cards (that's Tier 2, pending a Codex tool-interception adapter). The exact resume flags are unverified against a live Codex — override with `BIVY_CODEX_RESUME_TEMPLATE`. CI-tested via a stub codex in `test/process-resume.test.ts`. (`src/runtime/process.ts`, `src/runtime/index.ts`, `src/server.ts`.)
  - **Read-only Codex session adoption** — `GET /api/codex/sessions` and `/api/codex/sessions/<id>/messages` surface Codex sessions started outside Bivy (from its on-disk rollout under `$CODEX_HOME/sessions/**/rollout-*.jsonl`) as a reconstructed **read-only** chat, plus a `codex resume <id>` handoff to continue in a terminal. Codex has no launch-time session-id pin and its Bivy runtime can't yet govern/resume, so a *live governed* takeover is deliberately not offered for it — the rollout reader (`src/runtime/codex-sessions.ts`, unit-tested in `test/codex-sessions.test.ts`) is the read-side building block for when the Codex adapter deepens. The reader is best-effort and validated against the documented rollout format, not yet against a live Codex. (`src/runtime/codex-sessions.ts`, `src/server.ts`.)
- **Local CLI usability pass** — the `bivy` CLI is now genuinely useful without the web UI:
  - `bivy sessions` / `bivy ls`: list recent sessions (live `bivy run` PTYs + durable, resumable sessions) and resume a selected one. Live PTYs reattach; durable sessions reopen in the Bivy TUI via the new `bivy tui --session <ref>`. `bivy resume [n|id]` jumps straight to one. (`bin/bivy.mjs`, `src/tui.ts`).
  - `bivy run --node <name>`: start a session on another node (with `--agent`/`--model`). Direct routing via a `bivy nodes` registry (name → url + token, `.bivy/nodes.json`); `bivy token` mints a device token for pairing. Control-plane nodes are discovered/named but PTY tunnelling through the hosted relay remains a follow-up. (`bin/bivy.mjs`).
  - **Level B exec sandbox (opt-in)** — a Bivy-owned OS jail beneath each agent's Level A sandbox, Phases 1–2 of `docs/harness-exec-sandbox.md`: capability preflight + a hard-deny jail (bubblewrap on Linux with sensitive-dir masking, `sandbox-exec`/Seatbelt on macOS), wired into `ProcessRuntime` behind `BIVY_EXEC_JAIL=1`, surfaced in `/api/node/info.sandbox` and `bivy doctor --sandbox`. Off by default; passthrough when unavailable. (`src/harness/exec-jail.ts`, `src/doctor.ts`, `test/harness-exec-jail.test.ts`).
  - `bivy doctor` (health preflight), `bivy logs [-f]` (tail node logs), `bivy exec "<prompt>"` (one-shot headless, pipe-friendly), `bivy completions <bash|zsh|fish>`.
  - `bivy kill <id> [--delete]` (stop a session/run-terminal, new `POST /api/terminals/close`) and `bivy send <id> "<msg>"` (send a prompt to a session and stream the reply).
  - `bivy prune` (alias `bivy clean`): reclaim disk by removing old session transcripts (`.bivy/pi/sessions`), ephemeral `--clone` workspaces (`.bivy/workspaces`), and git worktrees (`*/.bivy/worktrees`) on this node. Retention is by count (`--keep N`, newest N of each kind survive) and/or age (`--older-than 7d|12h|30m|2w|<days>`); with both, an item is removed only when it is beyond the newest N **and** older than the age (safe intersection; default policy is `--keep 10`). Scope with `--sessions`/`--workspaces`/`--worktrees` (default all), preview with `--dry-run`, script with `--json`, skip the prompt with `-y`. Paths resolve from the real install — the node data dir (`.bivy`/`$BIVY_DATA_DIR`) and the configured workspace — and the primary workspace, Docker, and named volumes are never touched. A user-facing equivalent of the ops scripts `deploy/prune.sh` (age) and `deploy/prune-node-keep.sh` (count). (`bin/bivy.mjs`).
  - `bivy uninstall`: remove Bivy and all its data from this machine in one command — stops and deletes the background service, kills the running node, drops the `~/.local/bin/bivy` symlink, and removes the app install plus all local state (config, credentials, session transcripts, `--clone` workspaces) and the git worktrees Bivy created in your repos (`*/.bivy/worktrees`, with their git registration pruned). Deletes everything by default; opt out of your work with `--keep-sessions` (transcripts are moved aside and the new location is reported) and/or `--keep-worktrees` (repos left untouched). Preview with `--dry-run`, skip the prompt with `-y`. A source (git) checkout keeps its code — only the `.bivy` state dir is removed — while a packaged install is removed whole. Also deregisters the node from the hosted control plane. (`bin/bivy.mjs`).
  - **Git workspaces**: `bivy run <agent> --clone [remote]` / `bivy tui --clone` start a session in a fresh checkout (current repo or a given remote) under `.bivy/workspaces`; `--workspace <dir>` uses an existing directory.
  - **Sandbox depth**: the exec jail now also wraps `bivy run` PTYs, and adds a strict read-confinement mode (`BIVY_EXEC_JAIL_READS=strict`) that masks the whole home (denying secret + sibling-repo reads) while re-binding safe toolchains — the verifiable step toward native Landlock (see `docs/harness-exec-sandbox.md`).
  - **Relay-tunnelled `--node`**: verified client-side pairing/frame crypto core (`src/relay-cli-crypto.ts`, tested in-process against the real node `PairingStore`) so a CLI can reach a relay-only node E2E-encrypted; the transport + wiring is specified in `docs/relay-node-cli.md`, pending a live relay to build against.
